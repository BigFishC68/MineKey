
**关键安全项**：文件最高地址 `0x24DD`，远低于 `0x3800`。CH552 的 ROM BootLoader
固化在 `0x3800-0x3FFF`，用户区任何写入都碰不到它。这也是为什么前面那么多次失败、
反复擦写之后，芯片依然能进 BootLoader 的原因。

### 关于 `minekey.bin` 与 `.hex` 的 9 字节差异

`.bin` 比 `.hex` 的数据多 9 个字节，位置是：

```
0x0004-0x000A   （7 字节）
0x000E-0x000F   （2 字节）
```

这是 8051 中**未被使用的中断向量槽**，`.hex` 里不写这些地址，`makebin -p`
用 `0xFF` 填充。除这 9 个字节外，两者**逐字节完全一致（差异 0）**，同源无疑。

**① 失败点在写代码之前**

| 命令 | 结果 |
|---|---|
| Detect / 读配置 / 读 UID | 正常应答 |
| SetKey（设写密钥） | 正常，芯片回的校验和 `0xCA` 与计算结果完全一致 |
| FlashVerify（比对 flash 内容） | 正常应答 |

**③ hex 本身通过全部格式校验**
599 条记录校验和全对、EOF 存在、地址不越界、与 bin 逐字节一致（见第三节）。

**④ 供电已排除**

### 10.7 2026-11-11 18:30 根因定性：错的是**接线映射**，不是键表

**现象**：用户按物理丝印 CN1 的键，出的是 `4`；而驱动界面上 CN1 显示的是「光标↑」。

**推理（一步就定死了）**：

1. 当时的键表把 `4` 放在 key7（`0x0121`）
2. 物理 CN1 出 `4` ⇒ 物理 CN1 落在 **bit8 = (R3,C1)**
3. 说明 ROW1 是**上排**、ROW3 是**下排**，COL1..COL4 左→右

于是真实接线是：

| bit | 电气 | 物理 | 键索引 |
|---|---|---|---|
| 0..2 | R1C1..R1C3 | 上排 CN9 CN10 CN11 | 8 9 10 |
| 3 | R1C4 | 旋钮按压 | — |
| 4..7 | R2C1..R2C4 | 中排 CN5..CN8 | 4 5 6 7 |
| 8..11 | R3C1..R3C4 | 下排 CN1..CN4 | 0 1 2 3 |

代理一启动就刷屏 `[>] 下载文件夹`（3 秒内 9 次）。根因在 `keys_update()`：

```c
if (active_sw[k] == 0) {
    if (T_ACTION) run_action(...);            /* 没占住 active_sw */
    else if (T_HOST) host_action_pending=…;   /* 没占住 active_sw */
    else if (code) active_sw[k] = code;
}
```

`T_ACTION` / `T_HOST` 分支不写 `active_sw[k]`，于是"按下沿"判定永远成立：
**按住不放 = 每 1ms 触发一次**（1 秒上千次）。这既让主机动作看起来"乱发"，
也让"亮度±"类动作一按到底。

**③ 代理改为非阻塞轮询**

`agent.py` 由阻塞 `read(64,1000)` 改为 `set_nonblocking(1)` + `read(64,0)` + 10ms 轮询。
原因：配置器/其它工具同时打开同一个 HID 集合时，阻塞 ReadFile 会被抢占，

**关键点：失败发生在「写配置位」这一步，日志里「擦除中 / 编程中」一行都没有 —— 代码区一个字没被碰，芯片完好。**
之后仍能枚举为 `USB\VID_4348&PID_55E0`（BootLoader），说明只是进不去烧录流程。

17:57 那次成功（芯片 #3）日志里多一行 **`从用户区跳转BOOT,配置位禁止修改!`** ——
即工具当时**跳过**了配置位处理；这次没跳过，所以死在第一步。
（为什么状态会变，还没有定论；工具的把配置位状态存在
`WCHISPTool_CH54x-55x\CONFIG_CH54X55X.WCH`，mtime 20:39，可疑但未改动。）

**解决办法：走 `ispprog.exe` 命令行烧录器**（`…\WCHISPTool_CH54x-55x\ispprog\ispprog.exe`）

它内部调 `SetIspOption(1, mode=noprotect)`，**整体跳过配置位/保护位**，只做擦除+编程+校验：

```
[1] SetIspOption -> 1 (mode=noprotect)
[2] EnumDevices -> 1 台  dev0: index=0 mcu=0x00 (cold)
[3] 载入 minekey_led.hex  27264 字节（HEX 文本）
[4] FlashProgramB -> 1          ← 编程成功
[5] FlashVerifyB  -> 0          ← 该小工具未把校验结果计入结论，需实测确认
结果：成功
```

**注意**：必须先把 WCHISPStudio / WCHISPTool 全部关掉——它们会独占 HID 设备，
命令行工具能枚举到但 `FlashProgramB` 返回 0（打不开句柄）。这是第一次失败的真实原因。

烧完工具**不发"运行"命令**，芯片仍停在 BootLoader，需拔插一次 USB 才会运行用户程序。

新增 `tools/flash_cli.bat`（纯 ASCII，双击即烧，可传 hex 路径参数），作为日常烧录入口。
